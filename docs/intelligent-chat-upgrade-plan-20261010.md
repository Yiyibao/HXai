# MathStudyAgent 智能 Chat 优化升级方案

日期：2026-10-10。状态：四阶段实现已完成。原设计建议保留供对照，具体交付、修复和验证范围见 [验收报告](../qa/intelligent-chat-upgrade-20261010/report.md) 与 [实现/使用说明](intelligent-chat-upgrade-implementation-20261010.md)。

目标：在现有 Flutter + Android Kotlin 架构上，让聊天读起来稳定、任务过程清楚、交互有用、成果可以继续修改、长对话可以可靠继续。

本方案以当前代码、已有验证记录和本次读取的官方资料为依据。ChatGPT、Claude 的产品能力用于确定体验方向；下文的刷新周期、事件协议、缓存和上下文策略是本项目设计建议，不代表两家产品的内部实现。既有测试报告不替代本次升级验收。

## 1. 产品方向与参考依据

继续遵循“个人通用 AI 助手，Chat-first，Agent-extend”。数学是重要使用场景，日常问答、资料分析和文件处理同样属于核心场景。

| 参考产品能力 | 官方依据 | 本项目采纳方式 |
| --- | --- | --- |
| ChatGPT：从研究、文件输入到可审阅成果和后续修改 | [Use ChatGPT](https://learn.chatgpt.com/docs/use-chatgpt)、[Work with files](https://learn.chatgpt.com/docs/artifacts-viewer) | 聊天内完成任务；生成成果可预览、修改、保存和再次查找 |
| OpenAI 搜索 API：正文引用与来源标注 | [Web search / Output and citations](https://developers.openai.com/api/docs/guides/tools-web-search#output-and-citations) | 在相关结论附近提供可点击来源，来源抽屉作为补充；这是 API 展示要求，不能据此推断 ChatGPT 的内部架构 |
| Claude：成果可独立打开、编辑和迭代 | [Artifacts](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them) | 手机采用聊天摘要 + 全屏成果，平板可采用并排预览；保留旧版本 |
| Claude：可展开的思考区域 | [Thinking settings](https://support.claude.com/en/articles/8664678-change-the-model-effort-and-thinking-settings) | 默认折叠模型实际返回的推理内容或摘要；无返回时只显示真实等待状态 |
| Claude：根据任务区分搜索、复杂推理和研究 | [Search, thinking and research](https://support.claude.com/en/articles/11095361-when-should-i-use-web-search-extended-thinking-and-research) | 简单问题直接回答；时效信息按需搜索；多步骤任务显示简短进展 |
| Claude：历史检索、独立记忆、来源和管理入口 | [Chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context) | 区分原始历史、任务摘要和长期记忆，按当前档案检索，允许核对与纠正 |

对外体验的目标是：回应及时、内容平静易读、过程可信、可以自然追问。能力上限仍取决于当前模型、工具和服务；UI 优化不能替代模型推理质量。

## 3. 第一阶段：流畅、稳定的回复显示（P0）

用户效果：发送后马上看到反馈，文字持续出现，长答案不会随着每次增量反复闪烁，读历史时不会被拉回底部。

### 3.1 消息级流式更新

- 初次进入、恢复连接和历史加载仍使用会话快照。生成过程中按 messageId、partId 更新正在变化的内容。
- Kotlin 保留原始业务事件及持久化职责；Flutter 合并文本显示更新。先以 40 毫秒为默认起点，根据性能测量在 30–50 毫秒间调整。
- 首段内容优先展示；完成、失败、审批和工具状态立即处理；终止前刷新文本尾部。
- 拆出独立消息组件及消息级 Riverpod 订阅。旧消息及输入框不随当前文本增量重复执行昂贵解析。
- 不在业务流前增加可能丢弃关键事件的通用节流；文本展示可以合并，工具副作用和完成事件必须完整处理。

### 3.2 稳定增量 Markdown

- 缓存已完成块，只重新处理未完成末尾；跨块语法（列表、引用、表格、引用式链接）需要维护解析依赖，结束时进行完整校正。
- 流式展示可临时关闭尚未闭合的代码围栏，原始内容不变；不使用简单星号计数来盲目补齐强调语法。
- 不完整公式采用稳定占位或原文展示，完整后渲染；生成期间避免不断暴露低层解析错误。
- 普通回复代码块增加语言标题、复制、高亮及横向滚动。未知语言使用普通代码样式。
- 已完成内容保持可选择复制，复制数据来自原文。

### 3.3 排版与轻动效

- 保留正文行高 1.65 和文档布局。宽屏正文最大宽度建议 720 logical pixels；大表格和图表允许进入全屏。
- 图片按已有尺寸或合理占位保留空间，加载失败可重试。
- 新消息仅入场时采用约 180 毫秒淡入和轻微位移；Token 更新、重开历史、切换分支不重播。
- 遵循系统减少动画设置；发送可提供轻微触觉反馈。
- 保留现有 ChatTimeline，不因每批文本重新启动长滚动动画。

验收：长中文答案、混合公式与代码、宽表格、延迟图片、快速增量与突发增量均稳定；上滑、键盘、卡片内滚动和返回最新符合既有行为；结尾文字没有遗漏。

## 4. 第二阶段：清楚且可信的任务过程（P0）

用户效果：知道它在等待模型、思考、搜索还是处理文件；完成时看到结果，失败时知道下一步。

### 4.1 一轮回复的统一状态

统一表示等待、生成、执行工具、等待用户确认、完成、失败和中断。复杂步骤可以连续发生；工具状态与消息状态分别保留，不能把“工具结束”直接当作“整轮完成”。

- 点击发送后及时显示“正在准备回复”等真实状态，首个内容到达后让位于正文/工具状态。
- 模型实际返回推理时使用现有折叠区域；只显示所返回的内容或摘要，不为无推理能力的模型模拟思考文本。
- 工具调用保持真实顺序，重复步骤可折叠归组；默认只展示用户理解任务所需的信息。
- 审批沿用当前权限策略，展示将执行的具体动作。

### 4.2 可读的工具状态

| 工具行为 | 执行中 | 成功后 |
| --- | --- | --- |
| 网页搜索 | 正在搜索资料 | 找到 N 个来源，可查看 |
| 材料读取 | 正在读取相关内容 | 已读取对应文件/页范围 |
| 图表生成 | 正在整理图表 | 图表已生成，可调整参数 |
| 文件生成 | 正在生成文件 | 文件已生成，预览/保存 |

数量、页码、耗时和完成结果来自真实记录；未知时省略。工具名覆盖 search_web、图片检索、create_interactive_surface、render_math_plot 等当前已用能力，避免泛化为“处理步骤”。

### 4.3 来源和失败操作

- 保留来源抽屉，在关联结论附近增加可点击引用。编号或引用 ID 必须能解析到本轮真实来源；无法关联时不伪造引用。
- 中断后保留已经展示和已持久化内容，在消息原位显示“重新生成”“继续处理”或“检查执行结果”等适用操作。
- “重新生成”产生新分支；“继续处理”基于任务状态恢复。执行结果未知的有副作用工具先核对，避免重复生成、覆盖或交付。
- 状态变化采用约 150–200 毫秒轻过渡；不展示无依据的完成百分比。

验收：首 Token 延迟、搜索失败、工具异常、审批拒绝、网络断开、主动停止和应用重开均有正确状态；部分回答保留；不自动重复有副作用工具。

## 5. 第三阶段：让交互组件成为可迭代成果（P1）

用户效果：能操作图表、选项和文件，并让 AI 基于当前选择继续修改，而不必重新描述全部背景。

### 5.1 明确展示选择

| 内容目的 | 默认展示 |
| --- | --- |
| 解释、短问答 | Markdown 与必要公式 |
| 来源比较 | 表格，必要时加选择控件 |
| 数据趋势 | 图表 + 一段结论 + 来源 |
| 参数影响 | 滑块 + 图表/数值，本地计算 |
| 缺少关键偏好 | 少量选项或澄清卡片 |
| 可复用的长成果 | 聊天摘要 + 独立成果预览 |

避免同一份内容在正文、表格和卡片中完整重复。短答案不强制使用卡片；组件没有实际操作价值时用普通排版。

### 5.2 复用 v4 渲染能力

- 保留现有声明式协议与 Kotlin/Flutter 双端验证。完整且校验通过的静态组件可继续渐进显示；未完成 JSON 保持占位。
- 有输入、按钮、外部请求或依赖计算的组件，按照现有受限预览策略，在完整定义及权限确认后开放交互。
- 本地滑块、排序和筛选优先本地响应。只有用户点击“基于当前选择继续分析”等明确操作时才续聊。
- 续聊携带成果 ID、revision、当前用户选择及相关数据引用；避免无条件发送整个界面与全部历史。

### 5.3 成果迭代与建议

- 手机成果采用全屏预览，返回后保持聊天阅读位置；平板有空间时提供并排预览。
- 复用已有成果和版本能力，为图表、表格、交互界面和文件统一提供标题、版本、继续修改入口。
- 修改只影响目标成果；发生版本冲突时要求重新加载，而非静默覆盖。
- 支持针对可选择文字/表格项的“解释这里”“修改这里”，携带明确锚点。
- 回答后最多建议 2–3 个与当前内容相关的操作；完成型任务可以没有建议。点击后走现有发送管线，支持草稿保留和防重复提交。

验收：修改参数后续聊使用正确状态；离开/返回恢复；修改一个成果不污染其他成果；旧版本可访问；无工具能力模型可降级为文本，不宣称生成了交互组件。

## 6. 第四阶段：上下文与 Agent 行为升级（P1）

用户效果：简短问题回答直接，复杂任务持续推进；长对话不丢关键条件，相关历史可以找回。

### 6.1 表达和工具选择

- 在现有默认提示词基础上补充：先回答核心问题，默认自然段；按内容需要使用列表、表格和交互界面。
- 对简单问题直接回答。多步骤任务只给简短计划和必要进展，完成时交付实际结果。
- 只有缺少信息确实影响结果时才澄清；普通可逆本地操作沿用用户授权，不增加多余确认。
- 将工具描述按用途整理，按模型能力和任务选择必要工具。先评估路由再调用，不能因工具数量缩减而丢失隐含需求。
- 本地优先的文件策略、图片真实性、记忆保存成功条件、档案隔离和 MathStudy 数据边界继续生效。
- 用户自定义提示词不得被新版默认规则静默替换。

### 6.2 上下文预算

模型输入按四层组织：当前请求与约束、最近对话、任务摘要、按需检索的长期记忆/历史/材料。

- 实施前核对 Flutter 入口与已有压缩服务，优先复用。增加 Token 预算估算，并为工具返回和模型输出预留空间。
- 接近预算上限时压缩旧内容，原始记录仍保留。摘要保存目标、用户限制、已完成步骤、失败、待办、成果/材料 ID 和来源。
- 不拆开工具调用及其结果，不摘要掉未处理审批和工具结果未知状态。
- 压缩失败保留旧摘要，使用安全的上下文裁剪或明确提示；不能无限递归重试压缩。
- 以结构化“当前任务”状态支持“继续刚才的任务”。历史检索限定当前档案，命中可以跳转核对。
- 长期记忆与会话摘要独立；用户更正和删除继续遵循现有抑制规则。

### 6.3 模型能力适配

根据实际提供方能力控制思考、视觉和工具选项；需要时提供简洁的速度/深度选择。默认保持用户选择的模型，不暗中切换提供方或扩大成本。模型请求错误与前端刷新耗时分开记录。

验收：自动压缩后能复述关键条件并继续任务；摘要失败可恢复；工具边界完整；删除的记忆不复活；档案切换无数据串用；模型缺少某项能力时给出正确降级。

## 7. 技术实现边界

保持 Flutter + Android Kotlin + Pigeon + EventChannel + Room。Kotlin 是业务状态和持久化的唯一权威，Flutter 保存显示缓存及局部交互状态；本轮不引入第二份聊天数据库。

建议事件通道：

`模型/工具 → Kotlin 业务状态与持久化 → 带类型事件 → Flutter 消息状态 → 富文本/工具/成果组件`

事件可包括 message_patch/text_delta、reasoning_patch、tool_state、surface_preview、artifact_ready、generation_state、error；名称在实施时统一。事件携带 schemaVersion、profileId、contextEpoch、conversationId、messageId、generationId、sequence 和 revision，局部事件再携带 partId/toolCallId。

- 文本增量按序追加；快照按 revision 替换。不可将累计文本误当增量。
- 重复事件忽略，过期上下文拒绝，缺失事件或订阅恢复后从 Kotlin 重取快照。
- 事件是实时通知，不替代持久化。完成事件到达前必须刷新文本尾部并保证最终状态可重取。
- 当前 facade 会话详情转换涉及文件、工具及所有分支，优先把这类工作移出高频文本刷新路径。
- schema 变更保留旧历史兼容，分阶段切换；可回退到原来的快照刷新模式。

自带密钥模式继续使用现有 CredentialVault/Android Keystore。若未来提供平台密钥和统一收费，再另立服务器代理、身份与限流项目，不作为本次 UI 升级前置条件。

## 9. 验收标准

以下数值是升级目标，不是当前实测结果。

| 维度 | 标准 |
| --- | --- |
| 发送反馈 | UI 接受发送操作后约 100 毫秒内出现可见反馈；模型首 Token 时间独立统计 |
| 流式调度 | 正常活跃文本按约 40 毫秒合并；结束无尾部缺失，后台恢复取得最终快照 |
| 重建范围 | 增量主要影响活跃消息；用构建次数/解析次数证明历史内容没有持续重解析 |
| 流畅度 | 目标设备前台 60Hz 场景，profile/release 的可用性能模式中分别测量 UI/raster；以 p95 单线程帧耗时不超过约 16.7 毫秒、超预算帧低于 5% 为初始目标 |
